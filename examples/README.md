# Примеры

## Демо-сервер синхронизации (`server/`)

Один файл на Node (18+), без зависимостей. Хранит по одному JSON-снимку на токен и умеет ровно то, что нужно приложению: отдать и принять снимок. Это пример для знакомства с протоколом, а не готовый сервис.

```bash
npm run example:server              # http://localhost:8787
PORT=9000 DATA_DIR=./data node examples/server/server.mjs
```

В приложении: **Настройки → Облако**, адрес вебхука, например `http://localhost:8787/wh_tasks_mysecret123` (токен — часть адреса, от 8 до 64 символов: буквы, цифры, `_`, `-`). Кнопки:

- **Загрузить**: отправить данные с этого устройства на сервер.
- **Скачать**: получить данные с сервера и заменить ими данные на устройстве.

Снимки лежат в `examples/server/data/<токен>.json` (папка в `.gitignore`).

## Протокол

Один адрес `…/wh_tasks_<TOKEN>`, тело и ответы JSON, формат такой же, как у файла экспорта (`{ "format": "nextup", "schemaVersion": 1, "exportedAt": <мс>, "tasks": [...] }`).

| Запрос | Ответ |
| --- | --- |
| `GET` | `200` снимок · `404` на сервере пока ничего нет |
| `PUT` + снимок | `200` `{ "ok": true }` · `409` `{ "error": "server-newer", "exportedAt": <мс> }` · `400` не снимок · `413` больше 5 МБ |
| `OPTIONS` | `204` (CORS: приложение и сервер живут на разных адресах) |

Заголовки `PUT`:

- `X-Nextup-Synced-At: <мс>`: `exportedAt` снимка, с которым это устройство в последний раз обменялось с сервером (`0` — ещё не обменивалось).
- `X-Nextup-Force: 1`: записать, даже если на сервере данные новее (пользователь подтвердил).

### Как сверяются метки времени

Приложение хранит две метки: `changedAt` (когда данные на устройстве менялись в последний раз) и `syncedAt` (`exportedAt` последней синхронизации).

- **Скачать.** Если `changedAt` позже, чем `exportedAt` снимка на сервере, то на устройстве есть более свежие правки: перед заменой приложение предупреждает.
- **Загрузить.** Сервер сравнивает свой `exportedAt` с `X-Nextup-Synced-At`: если на сервере уже есть что-то новее нашей последней синхронизации (другое устройство успело загрузить своё), он отвечает `409`, и приложение предупреждает перед перезаписью.

## Ограничения этой схемы

Это грубый «обмен целиком»: побеждает та копия, которую пользователь подтвердил, слияния по записям нет.

- Две копии, менявшиеся независимо, не сливаются: одна заменит другую (после предупреждения).
- Часы устройств сравниваются между собой: если они сильно расходятся, предупреждения могут быть лишними или запоздавшими.
- Удалённые задачи не «воскресают», потому что слияния нет вообще.

Позже можно сделать более аккуратный контроль **по записям**: у каждой задачи уже есть `updatedAt`, нужны «надгробия» для удалений и слияние на клиенте. Формат снимка для этого уже подходит.

## Безопасность

- Приложение принимает адрес только `https://` (и `http://localhost` для разработки), учётные данные в адресе не принимаются.
- Токен — часть адреса, поэтому он попадает в журналы прокси и историю браузера. Берите длинный случайный токен и `https`.
- Демо-сервер не ограничивает число запросов и не шифрует данные на диске. Для реального использования поставьте его за обратным прокси с `https`, ограничением частоты и своими правилами хранения.
